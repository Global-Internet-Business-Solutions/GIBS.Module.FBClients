# DNN FBClients Module

## Purpose and source

This document records the behavior and data scope of the legacy DNN module as the baseline for its migration to Oqtane. The source module is adjacent to this workspace at `C:\Websites\DNN9\Website\DesktopModules\GIBS\FBClients`. Its DNN package manifest identifies it as **GIBS Food Bank Client Manager** (`GIBS.FBClients`, package version `1.1.5`). The module is implemented as DNN Web Forms user controls (`.ascx` and code-behind), with DNN module settings, role and portal services, and a SQL Server data provider/stored-procedure persistence layer. The DNN package manifest registers a sequence of versioned SQL install scripts; `SqlScripts\01.01.03.SqlDataProvider` contains later client insert/update/get-by-id procedures and fields such as `PrimaryIncomeSource`.

## Data and persistence domains

The legacy `Components\FBClientsInfo.cs` and `FBClientsController.cs` show that the module's data is substantially broader than a single client name:

- **Client**: names, suffix, DOB and verification, address and verification/geocode, phone/email, ID-card value/photo, caseworker, portal/module ownership, active/locked flags, client type, gender, ethnicity, language, disability, notes, review flag, one-bag rule, service location, and primary income source.
- **Additional family member (AFM)**: name, DOB/verification, relationship, suffix, middle initial, ethnicity and gender, linked to a client.
- **Income and expense**: type, description and amount linked to a client; used to calculate/display financial totals and eligibility/budget information.
- **Visits/orders**: date, notes, bag count, location, signature, and order status. The source documents order status values 0–4 from paper entry through text-link submission, processing, and filled order. Visits also drive last-visit and visit-eligibility displays.
- **Seasonal assistance**: Christmas-year records, sizes, toy interest/verification, received date, bike raffle/award, notes, gift fields, and AFM history/ticket/report operations.
- **Other persisted data**: client ID photos/signatures and per-client true/false questions.

The controller exposes search, client CRUD, family-member CRUD/search, client merge, visit CRUD/status changes, income/expense CRUD, Christmas assistance/current-year/history/ticket operations, age-group reporting, caseworker lookup, photo operations, and true/false question operations. DNN role, portal, list, localization, notification, mail, navigation, and settings APIs are coupled into the Web Forms code-behind. The module also references external/browser-side integrations and hardware-oriented workflows (Twilio SMS, Google geocoding, webcam capture, signature capture, and DYMO label printing); these are migration dependencies, not all self-contained server features.

### Activity and archive mappings

- Operational child tables use new generated primary keys and parent `FBClientsId` (or `VisitId` for visit items). Source identities are retained in nullable `LegacyVisitId`, `LegacyVisitItemId`, `LegacyIeId`, `LegacyTfId`, `LegacyImageId`, and `LegacyXMasId`. The inherited legacy audit fields remain separate from Oqtane audit values. Visit items had no source audit columns; their Oqtane audit values describe target creation/modification, not invented DNN history.
- Visits preserve nullable order status with an initial object/database default of zero. Signatures and ID photos use unbounded binary columns; ID photos remain required. `IeAmount` uses `decimal(19,4)` to preserve SQL `money` precision, without adding a source-money range restriction to the new schema.
- Visit-item `ProductId` retains the external catalog identifier, with no product table or product FK in this module. The importer must verify the source catalog/provenance; this field is not an Oqtane product identity conversion.
- Christmas records retain all supplied gift fields and nullable flags/dates. `LegacyClAddFamMemId` preserves the original reference, while nullable `FBClientsAddFamMemId` is the resolved target reference. The reviewed source procedure in `01.00.86.SqlDataProvider` writes a supplied family ID but does not establish a universal zero/sentinel convention. Import must explicitly classify unresolved/invalid references; a null target FK alone does not assert that a record belongs to the primary client.
- A composite Christmas-to-family FK requires any resolved family member to belong to the same client. It uses no-action deletion to avoid SQL Server multiple cascade paths and prevent silently deleting seasonal history when a family member is deleted. Client deletion cascades to its operational children. A future family-delete workflow must explicitly retain, reassign, or remove affected Christmas records.
- Merge archives have independent generated `ArchiveId` keys, required Oqtane `ModuleId`, and required original `LegacyRecordId` values. Their module/legacy lookup indexes are nonunique, so duplicate historical IDs are not silently discarded. Child archives retain `LegacyClientId`; client archives retain `LegacyMergedWithClientId` and original ownership/caseworker provenance. They have no active-client or active-family FK and survive operational client deletion; module deletion/uninstallation removes them.
- Archive fields follow each historical table rather than inheriting the operational entity shape: archived visit notes are unlimited Unicode, archived client middle initials allow 15 characters, and later visit/Christmas/client fields are not fabricated. Shared legacy audit properties are a CLR reuse mechanism, not an EF inheritance hierarchy.

### What the checked-in source tells us

- The DNN package contains **47 versioned SQL install scripts**. The baseline script creates client, additional-family-member, income/expense, and visit tables; later scripts add true/false questions, Christmas-assistance records, client ID photos, and merge-related tables. Client columns and procedures continue to evolve in later scripts. The scripts are an upgrade history, not a guaranteed snapshot of the deployed schema.
- The initial schema defines client IDs and child-record IDs as identity primary keys. The scripts add some child-to-client foreign keys with `WITH NOCHECK`; therefore, deployed referential integrity and orphaned rows need to be checked rather than assumed. The source also has multiple tables that must be migrated together to preserve a client's history.
- The Oqtane client/household schema now has its own generated keys, ownership, legacy provenance and audit columns. It is not a drop-in replacement for DNN's physical tables. Oqtane migrations use the module's migration/entity-builder pattern and database name rewriting; adding ad hoc columns to the DNN table would not make it an Oqtane module schema.
- The source merge procedure in `SqlScripts\01.00.30.SqlDataProvider` copies the losing client and its related records to six archive tables while preserving original IDs with `IDENTITY_INSERT`; the archived client stores the winning client ID in `mergedwithclientid`. It then reassigns family members and visits to the winner, inserts the losing client as a family member, deletes the losing client's questions/income/Christmas rows, and deletes the losing client. Archive rows are therefore historical snapshots, not additional active records to import into operational tables. The reviewed procedure does not explicitly move the separate ID-photo rows before client deletion. Confirm deployed procedure behavior and data before implementing merge/history or importing archives.
- The DNN `IPortable` export/import methods are **not a full-data migration path**. The export serializes only a client last name per client, while the import reads a different XML element name and inserts only a last name. It does not carry the related tables, settings, images, or full client records. Do not use DNN's module export/import for this migration.
- The stated scale—about **1 million records across all tables in one DNN instance**—is material but manageable with a planned SQL/bulk migration. The checked-in code does not provide live row counts, table sizes, blob sizes, or data-quality results; those require queries against the actual DNN database.

### Recommended default: new Oqtane-owned schema plus ETL/import

Create a coherent Oqtane data model and its tables through Oqtane module migrations, then perform a controlled, repeatable migration from the DNN database into those tables. Avoid modifying DNN-owned tables to serve as the permanent Oqtane schema, and avoid using the Oqtane web UI or per-row EF CRUD calls to transfer a million rows. This separates the DNN application from the Oqtane module's schema lifecycle, tenancy, and future upgrades, while allowing intentional cleanup and mapping of legacy data.

This recommendation assumes Oqtane should own its module data after cutover. If both systems must operate against the same physical database during a transition, sharing legacy tables can be evaluated as a deliberate compatibility architecture—but it would require confirming the Oqtane tenant/database arrangement, table naming, schema ownership, portal-to-site/module mapping, keys, and concurrent-write rules first. It should not be the default inferred from both applications using SQL Server.

For the new model, include the Oqtane `ModuleId` relationship and all required domain entities/relationships; do not add a generic Oqtane `Name` field to the DNN schema as a substitute. Retain the original DNN keys in explicit legacy-ID columns (or a dedicated old-to-new key map) so child records, reconciliation, and any external references can be mapped even if Oqtane generates new primary keys. Preserve DNN portal/module provenance where useful for auditing. Keep Oqtane-owned fields such as `ModuleId` and Oqtane audit columns distinct from the legacy DNN `PortalID`, `ModuleID`, and user IDs; do not silently treat DNN numeric user IDs as Oqtane users.

### Scale-appropriate migration sequence

1. **Profile the live source.** Back up the database, identify the installed module version and actual table definitions, and collect per-table row counts, storage sizes, min/max keys, null/duplicate statistics, orphan counts, and photo/signature byte totals. Include the merge tables and determine whether they are current operational records, historical snapshots, or both.
2. **Finalize target schema and mapping.** Define source-to-target column mappings, null/default/date/currency handling, identity strategy, ownership mapping from each DNN portal/module instance to an Oqtane site/module, and explicit disposition for unsupported/retired features. Resolve FK/data-quality exceptions as documented transformations rather than silently dropping rows.
3. **Implement and test Oqtane migrations first.** Create the normalized target tables, indexes, constraints and Oqtane module relationships, with indexes suited to the actual query patterns. Review EF types and lengths against the live DNN schema. Handle large photo/signature payloads deliberately—separate storage or optimized bulk loading may be preferable to holding them in ordinary row-by-row application operations.
4. **Build a repeatable, restartable bulk loader.** Use a controlled server-side ETL or a purpose-built importer using bulk-copy/batched SQL, not the DNN `IPortable` methods or a million HTTP requests. Load parent rows before dependents, preserve/map legacy IDs, use bounded batches and checkpoints, and make reruns safe (for example, upsert/deduplicate by source system plus legacy key). Record failures and counts per batch; do not report success when rows were skipped.
5. **Rehearse and reconcile.** Run full imports in a non-production environment, measure elapsed time and target storage/index growth, compare source/target counts and key sets per entity, validate foreign-key coverage and important aggregates, and sample high-risk records. Verify special cases such as merged clients, inactive/locked clients, null or invalid dates, year-specific assistance, and photos/signatures.
6. **Cut over with a defined consistency point.** If the DNN site remains writable during the initial bulk load, use an agreed delta-capture method or a brief write freeze plus final delta. Validate the final reconciliation, switch users to Oqtane, and retain a tested rollback/backup plan. Avoid dual-writing both systems unless conflict resolution and ownership are designed explicitly.

At one million rows, choose batch sizes and downtime from measured rehearsal results and payload/index sizes—not a guessed threshold. A single offline bulk load may be simplest if the business can freeze writes; online or low-downtime migration needs reliable change capture and a final consistency check. Database-native tools such as `bcp`/`SqlBulkCopy` are appropriate candidates, subject to the actual source/target database access and transformation needs.

## Migration considerations / open verification

1. Model the final DNN schema and data from the complete ordered install-script history and the deployed database before designing Oqtane entities. The source includes many incremental SQL scripts, and a single initial or latest script is not necessarily a standalone schema definition.
2. Define parent/child ownership and data migration rules for clients, AFMs, visits, income/expenses, Christmas records, images/signatures and question responses. Preserve legacy identifiers or provide a documented mapping where external links/reports depend on them.
3. Re-establish authorization explicitly: legacy behavior includes a configurable client-manager role and a separate delete-record role, while Oqtane currently uses module View/Edit permission policies. Confirm which actions require elevated rights and how module/site tenancy maps to legacy portal scoping.
4. Review all configurable defaults, required-field rules, bag/visit eligibility calculations, client-type differences, and Christmas qualification logic in the DNN implementation before replacing them. Do not infer business rules from the generic Oqtane starter model.
5. Choose replacements or explicitly retire external/hardware workflows (Twilio, geocoding, webcam, signature tablet, DYMO labels, barcode/ID cards, email/notifications) and test the resulting user journeys.
6. Plan for sensitive personal information (DOB, address, contact details, household composition, disability, income, photos and signatures): access control, logging, export, retention, and migration handling need to be reviewed as part of the port.
